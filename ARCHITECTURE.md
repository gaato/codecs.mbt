# Architecture

This repository holds pure-MoonBit codecs that decode and encode as data
arrives: input in chunks of any size, output into slices of any size, and
memory bounded by limits the caller sets. Each format is its own module with
its own version; the modules share a small vocabulary, a few building blocks,
and one way of testing.

## Layers

```
consumers     command-line tools, HTTP clients, applications
                │ depend only on a kind's contract and gaato/codec's errors
──────────────┼───────────────────────────────────────────────────────────
formats       zstd  brotli  deflate     │  png            │  audio formats
                one module per format; a format may embed another codec
──────────────┼───────────────────────────────────────────────────────────
contracts     gaato/codec_bytes          │  gaato/codec_image │ an audio contract
  per kind    byte stream in, bytes out  │  pixels, by rows   │ samples, by blocks
──────────────┼───────────────────────────────────────────────────────────
vocabulary    gaato/codec: errors, limits, resources
──────────────┼───────────────────────────────────────────────────────────
building      bit readers and writers, checksums, prefix-code tables,
blocks        entropy coders: small, mostly pure functions
```

The byte-stream contract and the compression formats exist today: zstd,
brotli, DEFLATE with its two containers, zlib and gzip, in one module of
three packages (`gaato/deflate`, `gaato/deflate/zlib`, `gaato/deflate/gzip`),
Snappy (`gaato/snappy`), whose raw format is whole only and whose framing
format streams, LZ4 (`gaato/lz4`), whose frames stream and whose blocks
are whole, and LZW (`gaato/lzw`) in the flavours of GIF, TIFF, PDF and .Z.
So do the image contract, `gaato/codec_image`, and its first format, PNG with
APNG (`gaato/png`). The audio row shows where such codecs would go; nothing in
the layers below has to change for them. One building block is also a module
of its own for callers that need it: `gaato/crc`, any CRC of up to 64 bits,
with copies of the same CRC-32 and CRC-32C parts the formats take.

**Vocabulary.** `gaato/codec` holds what every kind of codec reports in the
same terms: the error kinds, and the limits a stream can exceed, in bytes. A
command-line tool or a fuzzer handles a failure the same way whatever it was
decoding. The error kinds and resources are `#non_exhaustive`, so a new kind
of codec can add what it needs without breaking anyone.

**Contracts, one per kind.** Bytes, images and audio come out in different
shapes, so each kind has its own contract module: the steps a codec takes,
what a step reports, and the rules every codec of that kind keeps. They are
separate modules because a module's version covers all of its packages, and
an image contract that is still settling should not force a new version on
every compression codec. The rules are the same for every kind: errors stick,
a codec never reads past what it needs, results do not depend on how input
and output are split, and memory stays within the limits it was given. The
byte-stream and image contracts are written down in
[CONTRACT.md](CONTRACT.md).

**Formats.** Each format is one module. A format that contains another embeds
that codec as a value (a PNG decoder holds a zlib decoder, which holds an
inflater), rather than reaching into its internals. Formats own their state:
a codec allocates what a stream needs, never more than its limits, and
reports it through `memory_usage`.

**Building blocks.** What several formats share is small and stable: reading
and writing bits in the orders formats use (LSB first, MSB first, backwards),
checksums, building canonical prefix-code tables, table construction for
entropy coders, the match finders of LZ77 encoders. They are written as pure functions where possible, which is
also where the proofs live. The decoding loops of each format stay inside the
format: they are tuned to it, and sharing them couples formats that change for
different reasons. A block moves out of a format when a second format needs
it.

The blocks have one source, in [`parts/`](parts/README.md): a private module
of the workspace, where they are tested once, and proved once where `moon
prove` can. Each format's module carries copies of the files it uses, under
`src/internal/`, generated by `scripts/gen_parts.mbtx` from the list in
`scripts/modules.json`; each copy names its source on its first line, and the
gates fail when a copy differs from it. The blocks are not a published module
of their own because moon's resolver treats every 0.x version of a module as
compatible with the others: a shared module would tie every format to whatever
version of it any format needs. With copies, each format keeps its own version
and depends only on the contract modules.

## What a step looks like

A byte-stream codec's step consumes input, fills output, and says why it
stopped: done, needs more input, or needs more room. Kinds whose output has
structure add events to that answer. An image decoder's step can stop to
report the image's header, the start of a frame, rows it has written,
metadata it was asked for, or the end of a frame; an audio decoder's step reports the stream's parameters
and blocks of samples.

Codecs do not hold a whole frame unless the format leaves no choice. A PNG
decoder keeps the previous row and the current one; interlaced images come
out pass by pass, and assembling the final image is the caller's choice.
Where a format does require buffering, the codec states it as a limit.

Conversions between pixel or sample formats are functions outside the codecs:
a codec produces its format's own layout, and the caller converts if it wants
another.

Recognising a format from its first bytes is a function that returns what it
found. Nothing registers itself; callers choose which codecs they link.

## Testing

Every codec is held to its kind's rules by one test harness, kept in a private
module of the workspace and never published:

- results are the same however input and output are split, down to one byte
  at a time, for corrupt input too: the same output before the same error;
- errors stick, truncated input is reported, nothing past the end is read;
- memory stays within the limits, checked after every step;
- corrupted input never crashes, and the kinds of error it causes are
  recorded;
- output matches the reference implementations (zstd, google/brotli, zlib;
  for PNG, pypng and the png crate), and so do the refusals of crafted and
  corrupted streams, where the reference can be asked (zlib, through Node).

Each module also keeps two ledgers that scripts enforce: RESOURCE_BOUNDS.md
names the tests that hold every bound, and TEST_COVERAGE.md explains every
line that tests do not reach.

## Unchecked access

The hot loops of the decoders and encoders (bit readers, match copies and
match finders, Huffman and prefix-code tables, PNG's filters, CRC-32) read
and write without index checks, through `unsafe_get` and `unsafe_set`, and
on native and Wasm through core's unaligned `unsafe_read_uint32_le` and
`unsafe_read_uint64_le` as well. Each bounds-checked access on Wasm calls
two out-of-line helpers (the length and the range check), and native spends
a compare and a branch on each: the slice-by-8 CRC-32 of 512 KiB took
1.25 ms checked and 0.53 ms unchecked on Wasm, 0.68 and 0.48 ms on Wasm GC,
0.33 and 0.29 ms on native. They follow these rules:

- **Wide reads on native and Wasm only.** Loads of four or eight bytes at
  once, and SIMD (below), sit behind
  `#cfg(any(target="native", target="wasm"))`, where they exist and pay;
  JS and Wasm GC read a byte at a time there, and their match finders keep
  checked accesses. Accesses of one byte whose bounds the loop itself
  establishes are unchecked on every target: the decoders' refills, copies
  and table lookups, the CRC-32 of `parts/crc32`, and `parts/blit`.
- **Every unchecked access says why it is in bounds**, at the access or on
  the helper it goes through (`Caller guarantees 0 <= p and p + 8 <= ...`).
  A wide read near the end of the data falls back to a byte loop that reads
  only valid input; a copy that may write past its end (the decoders'
  `wild_copy`) runs only where the slack is known to be free.
- **Bounds that can come near the largest `Int` are compared as
  differences**, `n - i >= 8` and not `i + 8 <= n`, so that such an index
  cannot wrap past the check. Loops within a block, a ring or an input
  chunk, whose sizes stay far below it, also compare sums.
- **The checked targets are a cross-check, not a proof.** The tests and
  the SHA-256 of every encoder's output run on all four targets, so a wide
  read that strays on native or Wasm can show up as a result that differs
  from JS and Wasm GC, which read a byte at a time there; a stray read
  whose bytes go unused shows nothing. The unchecked accesses rest on their
  stated reasons, and on the tests that drive them to their bounds: input
  and output split down to one byte, truncated and corrupted streams.
- **Proofs stay.** A proved function made faster keeps its proof: PNG's
  filters, reversed a pixel lane at a time, are still checked by `moon
  prove` to read and write only inside their rows. Code the prover cannot
  check, such as SIMD, sits beside the proved reference instead, as below.

## SIMD

A few loops run sixteen bytes at a time with core's `@v128`: the zlib
decoder's Adler-32 (`deflate/src/zlib/internal/adler32_fast`), PNG's Up
filter, and its Sub, Average and Paeth filters a pixel of 3 or 4 bytes at a
time (`png/src/internal/filter_fast`), and the match length of the
encoders (`parts/match_length_fast`) and the Zstandard encoder's row tag
comparison (`zstd/src/internal/row_tags_fast`). They follow these rules:

- **Native and Wasm only**, through `#cfg(any(target="native", target="wasm"))`.
  On JS, `@v128` falls back to code some 300 times slower than a plain loop;
  Wasm GC cannot load sixteen bytes from an array at once, so it gains
  nothing. The other targets keep the plain loop.
- **Operations that native lowers to few instructions.** Native lowers
  `@v128` through `moonbit_simd.h` (in the toolchain's `include`), one branch
  for SSE2 and one for NEON, where some Wasm instructions become several:
  Adler-32 written with `extmul` and `extadd_pairwise` ran 1.7 times as long
  on x86 as with widening and `i32x4_dot_i16x8_s` (one `pmaddwd` on SSE2,
  three instructions on NEON). Read both branches of that header before
  choosing; the timings are from x86 only, and arm64 runs the tests.
- **In a package of its own, next to the proved reference.** A proved
  function's body cannot hold a SIMD operation (`moon prove` refuses them as
  primitives), so the reference stays as it is, and the fast package's tests
  compare the two at every alignment, around every block boundary and on the
  inputs with the largest sums. Where the fast code reads a `FixedArray`, it
  is proved too: the SIMD operations sit behind trusted bridges whose
  contracts state only where they read and write, and `moon prove` checks
  that every sixteen-byte access lies within the array (`filter_fast`).
  Adler-32's reads go through `ArrayView`, which the prover does not model,
  so `adler32_fast` rests on its tests.
- **Confined, because `@v128` is experimental.** The fast package silences
  the experimental alert for itself only. If core changes `@v128`, pointing
  the `#cfg` branch at the reference restores the plain loop without
  touching anything else.

CRC-32 (gzip and PNG) does not use carry-less multiplication
(PCLMULQDQ). Neither `@v128` nor Wasm SIMD has the instruction, so it would
take the repository's first C stub, on native only. The stub could be built
with `-mpclmul` through the package's `stub-cc-flags`, but that flag is
x86's alone and lets the compiler use the instruction anywhere in the stub,
so the stub would need its own check of the CPU, a fallback, and another
for arm64. The CRC is about 4% of decoding PNG's benchmark image; the
slice-by-8 loop without index checks is what it uses instead.

## Parallelism

The codecs run on one thread. MoonBit's core has no public way to run
MoonBit code on several threads (`core/async`'s workers are for blocking
I/O), and encoding blocks independently would change the output, which the
encoders keep the same whatever the input's splits.

A caller with threads can still split the work, since the formats allow
it: a Zstandard stream may hold several frames and a gzip stream several
members, and the decoders read every one in turn. Encoding each piece with
its own `Encoder` and concatenating the results gives a stream that
these decoders read, as does any decoder that reads every frame or member,
at the cost of the matches across the pieces' boundaries.
Raw DEFLATE, zlib and Brotli streams cannot be concatenated this way.

## Speed work left out

Changes measured or considered and not made, with why, so that they are
not taken up again without new numbers:

- **A margin after the Zstandard decoder's ring**, so that every match copy
  could write eight bytes at a time past its end. It would add to
  `memory_usage` and the bounds in RESOURCE_BOUNDS.md; the decoder copies
  that way only where the ring already has the room.
- **Sizing the Zstandard decoder's ring from the frame's content size.**
  That would allocate what a header claims before any output proves it;
  the ring grows with the output instead.
- **Block copies through `Uint8Array.copyWithin` and `set` on JS.** They
  need `extern "js"`, which the repository does not use; `parts/blit` is a
  forward loop without index checks there.
- **SIMD Adler-32 in the zlib encoder.** The encoder reads a `BytesView`,
  the SIMD package an `ArrayView`, and the checksum is 2.4% of encoding.
- **A 64-bit bit reader in the Brotli decoder.** After the three-byte
  refills, refilling and reading bits are 1.6% and 2.7% of decoding.
- **A 64-bit bit writer in the DEFLATE encoder, and the Huffman builder
  without index checks.** The writer's bound on its output is not local to
  it, and the builder, about 3% of encoding, is in a shared package whose
  functions are proved.
- **Changes that alter an encoder's output** (a one-slot hash table or
  five-byte hashes in the Brotli encoder, skipping literal runs, other lazy
  matching limits): the speed work kept every encoder's output byte for
  byte, which the SHA-256 checks and the compression ratio tables hold.

## Where things are not

Archives and containers with entries or random access (tar, zip) build on
codecs from their own repositories: gaato/zip is in
[archive.mbt](https://github.com/gaato/archive.mbt). So do byte-stream codecs outside
compression (base64, character sets, encryption): implementing
`gaato/codec_bytes` needs only a dependency on it.
